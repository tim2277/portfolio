## The obvious version, and why it disappoints

The tempting first move is to point an agent at the diff and ask it for
comments. It works, in the sense that comments appear. Whether any of them are
worth the reviewer's attention is a different question.

Three things go wrong, reliably:

1. **Volume without ranking.** Twenty observations, no signal about which two
   matter. Reviewers learn to skim, then learn to ignore.
2. **No repo context.** The agent flags a pattern that's deliberate and
   documented, because it never read the document.
3. **Confident wrongness on the interesting bits.** Easy findings are correct.
   The subtle concurrency one is confidently, plausibly wrong.

## What actually helps

Constrain the job. An agent that only answers "does this change break an
existing contract?" is more useful than one asked to review everything, because
the question has a checkable answer.

```ts
// Narrow the brief, and the output gets checkable.
type ReviewFinding = {
  claim: string;
  file: string;
  line: number;
  /** The concrete input that makes it fail. Without this, it's an opinion. */
  failureScenario: string;
};
```

| Task | Agent | Human |
| --- | --- | --- |
| Contract/API breakage | Good | Tedious |
| Style and consistency | Good | Waste of a person |
| Is this the right design? | Poor | The whole job |
| Security-sensitive logic | Assistive only | Required |

## Where this goes next

The useful frame isn't "can it review code". It's "which questions have a
failure scenario you can write down". Those are the ones to automate first.
