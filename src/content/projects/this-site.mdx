<Summary>
  A static Astro site on Azure Static Web Apps: a pipeline that builds the site itself and uploads only `dist`, and exactly two scripts, each pinned by hash in the security headers. Most of this page is about the things that fail without telling you, the confessions a security review got out of me, and how version 1.1 added full-screen images, diagrams, labelled AI art and a narrator called Brian, all without a third script.
</Summary>

On one moderately coolish day in September 2026, I decided to build this site. Of course, the first builds were flawless, not a single issue! Green tick, clean exit code, no warnings, and not a single stylesheet in them. The culprit was my own machine: `C:\repos` is a junction onto another drive, Vite resolved the modules on one side of it while Astro tracked the other, and the CSS fell through the gap without a word. One line of config fixed it (`preserveSymlinks`, if ye've a junction of your own).

This page takes ye through the technical side, and it'll be updated as new versions are released (as demanded by my investors). A static site has very few moving parts by definition, but that doesn't mean engineering discipline goes out the window. What follows is how the site is put together, and every place it has failed silently on me so far.

## The stack, briefly

| Layer | Built with |
| --- | --- |
| Site generator | [Astro](https://docs.astro.build/) 7, static output |
| Content | [MDX](https://mdxjs.com/docs/) in content collections, [Zod](https://zod.dev/)-typed frontmatter |
| Styling | One hand-written stylesheet, CSS custom properties |
| Type | [Fraunces](https://github.com/undercasetype/Fraunces)[^fraunces], self-hosted, for headings; system stacks below |
| Syntax highlighting | [Prism](https://prismjs.com/), not [Shiki](https://shiki.style/) (see the confession below) |
| Hosting | [Azure Static Web Apps](https://learn.microsoft.com/en-us/azure/static-web-apps/), Free tier |
| Narration | [Azure AI Speech](https://learn.microsoft.com/en-us/azure/ai-services/speech-service/), [Ogg Opus](https://opus-codec.org/)[^opus-codec] files in [Blob Storage](https://learn.microsoft.com/en-us/azure/storage/blobs/) |
| Infrastructure | [Bicep](https://learn.microsoft.com/en-us/azure/azure-resource-manager/bicep/overview): the site, and the storage for the audio |
| Pipeline | [GitHub Actions](https://docs.github.com/en/actions), SHA-pinned, deploys from `main` only |

## Content is typed, not trusted

The site's collections - `posts` and `projects` - share a Zod[^zod] schema for title, description, date, tags and draft status, with projects adding a status enum and optional repo/live links. If something's off in the frontmatter the build fails, so I won't accidentally post a half-completed thought or, worse, a syntax error _gasp_.

Drafts render in `astro dev` and nowhere else: a production build leaves them out, and a description over 160 characters doesn't build at all.

## Two scripts, and what they cost

This site started with a guideline (Claude says it was a rule): no client-side JavaScript on a content page. Dark mode followed `prefers-color-scheme` and that was the end of it. The rule held until the first person asked for a theme toggle. That person was me, after looking at the boring <abbr title="user interface">UI</abbr> I had just built.

So there was exactly one script. It sets a `data-theme` attribute before `<body>` parses, reads and writes one `localStorage` key, and falls back to `prefers-color-scheme` when it doesn't run. About thirty lines, no dependencies, no framework - the type of efficiency that software dev promises but rarely achieves.

It wasn't free, and the bill is the interesting part:

- **The <abbr title="Content Security Policy">CSP</abbr> pins it by hash.** Having co-authored a few internal docs on ISO standards over the years, this was the first thing to set my cyber senses tingling. The boring technical bit: `script-src` carries a sha256 of that exact script rather than `'self'`, so nothing else can execute (cybersecurity win!).
- **Every themed rule now has two routes.** The OS preference when the reader hasn't chosen (dark for those L337 hackers and light for everyone else), `[data-theme]` when they have.

Then there were two, and this page spent an evening being wrong about it. After launch I decided the site was too plain and filled the wide-screen margins with a drifting pattern of matrices and maths symbols. It moved as you scrolled, all in CSS: no script, rule intact. It worked right up until you swiped past the end of a page a few times on a touchpad, at which point Edge stopped drawing the page for a second or more. Nothing was busy, nothing errored, and no amount of tuning the CSS changed it. Moving the same pattern from a dozen lines of script did.

So the second script exists to work around a browser. It gets its own hash in the CSP, and with scripts blocked the pattern simply stands still. Ye on a phone never see it at all: it only shows on a wide screen.

## Infrastructure

It's always great to design the best and coolest thingy, but if no one can see it or read it or touch it - then it's really just décor. So I made it easy: **one Bicep file** (keep it <abbr title="Keep it simple, stupid">KISS</abbr> and <abbr title="Don’t repeat yourself">DRY</abbr>!). The pipeline owns the deployment; Bicep owns the resources.

It stayed one file until Brian (the AI voice that reads the posts aloud, he's a sound lad) needed somewhere to keep his recordings. The storage account is a second Bicep file, pulled in as a module, with one public container for the audio and a role assignment so I can upload to it.

## The pipeline, and the Oryx detour

The default Static Web Apps workflow hands your repository to Oryx[^oryx], Azure's build engine (so thoughtful!), and lets it work out how to build the site. It'll happily build Astro[^swa-frameworks], to be fair. That's convenient right up until you want any customisation: a pinned Node.js version, a type check before the build, or a failure you can actually read.

> _"Sometimes the absence of something is all you need"._ - Tim in September 2026

That led to the current pipeline:

<Pipeline label="From a push to the live site" caption="Every push to main, from my keyboard to your browser. A red cross at any step and nothing reaches Azure, which is the only kind of failure on this page that isn't polite.">
  <Step title="⌨️ Push" by="Tim" human>
    To `main`, the only branch that deploys.
  </Step>
  <Step title="📦 Install" by="GitHub Actions">
    `npm ci` on a pinned Node.js, every action pinned to a commit.
  </Step>
  <Step title="🔍 Check" by="GitHub Actions">
    `astro check` for the types, then every narrated page against its script.
  </Step>
  <Step title="🏗️ Build" by="GitHub Actions">
    `astro build`, then every `#fragment` link checked against the page it points at.
  </Step>
  <Step title="🚀 Deploy" by="Static Web Apps">
    Uploads `dist` and nothing else. Oryx never wakes up.
  </Step>
</Pipeline>

The step that matters is the last one: the deploy action runs with `skip_app_build: true`, so it uploads `dist` and nothing else.

<Callout type="tip" title="The gotcha">
  With `skip_app_build`, `app_location` stops meaning "where the source is" and starts meaning "where the built output is". And because only `dist` gets uploaded, `staticwebapp.config.json` has to be inside it - so it lives in `public/` and Astro copies it across. Leave it at the repository root and it's silently ignored: no error, no headers, just a site that scores badly on a security scan for no visible reason.
</Callout>

Another planned feature was a preview before publishing to <abbr title="general availability">GA</abbr> - not doing that is like forgetting to put pants on, and that just isn't comfortable for anyone. Pull requests used to get their own preview environment, torn down again when the PR closed. Then a security review pointed out two things: I'd never opened a single pull request, and that preview job was the only reason a stranger's fork could run anything in my repository's workflows. So it went. Previews happen in `astro dev` now, and `main` is the only thing that deploys. Thankfully, a static site barely differs between dev and GA!

The rest of the pipeline got the same treatment. Every action is pinned to a commit SHA rather than a tag someone else can move, and the deploy token lives in a `production` environment that only `main` can reach.

## Headers and caching

**Cache all the things!\***

<small>
  \*: `staticwebapp.config.json` sets a CSP that starts from `default-src 'none'` and allows back only what the site uses, <abbr title="HTTP Strict Transport Security">HSTS</abbr>, `nosniff`, a referrer policy and a `Permissions-Policy` that switches off hardware APIs this site shouldn't be asking for. Astro's hashed assets under `/_astro/` get a year of immutable caching; HTML gets `must-revalidate`, so a deploy is visible immediately.
</small>

A strict policy has a habit of being right in ways that look broken, and two of the 1.1 bug fixes were exactly that. The feed and the sitemap opened in Edge and Chrome as a wall of run-together text (it looked like someone had vomited words onto a page). Broken feed, surely? Not this time. Chromium draws its XML tree view with an inline stylesheet and `data:` icons, inside a document that inherits the page's CSP, and `style-src 'self'` showed both of them the door. So the XML routes carry their own policy now, letting in exactly those two things and not a byte more (I can't stand walls of text).

Then Edge's Immersive Reader started showing a broken image above every alt text. Turns out it rebuilds the article under a `read://` address and fetches the images from there, and `Cross-Origin-Resource-Policy: same-origin`[^mdn-corp] turned every one of them away. The page itself looked grand, so nothing pointed at the header (sound familiar?). Images under `/_astro/` now go out as `cross-origin` (the web's default anyway), and the pages keep `same-origin`.

So the policy isn't one policy. Here's what each route sets on top of it, and why:

| Route | Sets | Because |
| --- | --- | --- |
| `/*` | `Cache-Control: max-age=0, must-revalidate` | A deploy is visible straight away |
| `/_astro/*` | A year of immutable caching, and CORP `cross-origin` | The file names carry a hash, so they never change; Immersive Reader fetches from `read://` |
| `/favicon.svg` | A week of caching, and CORP `cross-origin` | Same reader, same fix |
| `/rss.xml`, `/sitemap*.xml` | Their own CSP, allowing inline styles and `data:` images | Chromium's XML tree view, and only that |

Now the confession, or there was one. The first version of this page admitted that `style-src` carried `'unsafe-inline'`, with two culprits: Astro inlining its smaller stylesheets straight into the page, and Shiki[^shiki] writing every syntax colour as an inline `style` attribute. I'd decided to live with it.

Then a security review found a third culprit I hadn't: the hero image's crop, passed in as a `style` attribute. Three was enough. Stylesheets now always ship as files (one line of config: `build.inlineStylesheets: 'never'`), the hero takes its crop from data attributes, and syntax highlighting runs on Prism[^prism] instead of Shiki: it classes tokens rather than inlining a colour per span, so the CSP needed no exception for it. `style-src` is `'self'` on every page.

So go ahead and View Source, which - let's be honest - you were going to do anyway. This time there's nothing to find.

## 1.1, and still two scripts

Then along came version 1.1, codenamed "Chocolate Chip" (I just made that up, there was no codename - but the investors love it). It shipped three weeks after launch, and the [release post](/posts/this-site-1-1/) is the fun version. Here we talk about the tech and what each feature cost. The rule for all of them was the same: a page does its whole job with scripts blocked, and `script-src` doesn't move. None of them added a third script, and none added a dependency - surprisingly, thanks to a bit of advocating by Opus (Anthropic's Claude model and my partner in building this site).

### Full screen, in plain HTML

Images, wide tables and diagrams all open full size now, and none of it is JavaScript (amazing what modern browsers can do!). The `popover` attribute[^mdn-popover] does the lot: a button with `popovertarget` opens the element, and the browser looks after the backdrop, the Escape key and the focus. Nothing needs a hash. A browser that doesn't know the attribute gets a plain link to the full-size image, which is what it had before.

Funnily enough, tables were the reason the full-screen feature started. The [texturiser post](/posts/texturiser/) had a five-column table that pushed the whole page sideways on a phone. Now a Markdown table with four or more columns, on a screen under 44rem, keeps its columns readable, fades out at the edge, scrolls sideways, and gets a button that opens the whole thing in a popover. The posts didn't change: the entry routes map every Markdown table onto the component. "Four or more" is a fixed number rather than a measurement, which is a known limit and a fair price for no script.

The trap, because there's always one: the overlay holds a second copy of the caption or the table, and a footnote marker in that copy repeats an id and scrolls the page behind the backdrop when clicked. So the copy loses its markers.

### Diagrams without a diagram library

Two posts wanted a pipeline diagram, and the obvious answer was [Mermaid](https://mermaid.ai/open-source/). `mermaid.js` on the page breaks the site's ~rules~ guidelines, so Opus talked me out of it (it does that).

What shipped is a `Pipeline` of `Step`s: an ordered list in HTML and CSS, styled as cards and arrows. It follows the theme toggle, runs off the article's edge in one row and opens full size in a popover, and drops to a single column under 48rem. Take the stylesheet away and it's a numbered list, which is what it was all along. A step that repeats says so in words, because a list can't draw the arrow back. Agentic AI wins the day over a third-party dependency!

As someone who regularly plans development well ahead, I worry about future-proofing. These lightweight diagrams are great, but they draw a sequence and nothing else. The day a diagram needs to fork, Mermaid rendered to SVG at build time is the likely answer, and an untested one.

### Posts by month

Once I'd written enough for ye, `/posts/` needed grouping: by year, then by month, under real headings, with a contents list beside it: sticky on a wide screen, a closed `<details>` ("Jump to a month") below 64rem. The anchors are the dates themselves, so `/posts/#2026-10` goes where you'd expect. No archive pages like `/posts/2026/10/`, by choice.

Two details took longer than the feature. A closed `<details>` can't be reliably forced open without script, so the list of months is in the page twice and the stylesheet shows one of them. And dates are read in UTC: frontmatter dates are midnight UTC, and a build machine west of [Greenwich](https://en.wikipedia.org/wiki/Greenwich) would otherwise file a post from the 1st under the month before. (Ireland is west of Greenwich too, but our clocks never fall behind it, so we're grand.)

### AI images, labelled

On a site about AI, there's one thing I believe matters: _transparency_. So every image a model had a hand in says so three times, set by two arguments that have to agree:

| Where | What it says | Set by |
| --- | --- | --- |
| The pixels | `AI-generated` or `AI composite`, burnt into a corner | The converter's `-Ai` |
| The file | The <abbr title="International Press Telecommunications Council">IPTC</abbr> digital source type[^iptc-source-type] | The converter's `-Ai` |
| The page | The European Commission's AI icon[^eu-ai-icons], with the kind as its hover and screen-reader text | `Figure`'s `ai` prop |

<Figure src={aiLabel} ai="composite" alt="Two zoomed-in crops of the cast photo on a plain grey background. Above, the top-left corner, where a white circle reading AI sits over the red frame, beside a faceless figure in round glasses. Below, the bottom-right corner, where a small dark label reads AI composite · timwrites.dev over Brian's script. In the grey margin at the very bottom right, a second, smaller label reads the same.">The icon and the burnt-in label, close up. And yes, the picture of the label has a label: it's a crop of an AI image, so it gets one too.</Figure>

The folder decides the licence as well: anything in `src/assets/generated/` has its own scope in the `LICENSE`, on the same <abbr title="Creative Commons Attribution-NonCommercial">CC BY-NC</abbr> terms as the writing.

The trap: nothing checks that the prop matches the file, or that an image in that folder went through the converter at all. Astro also drops the source type from every copy it re-encodes, so it survives in the committed file only. I'm grand with that. The burnt-in label is the one that travels.

### Brian reads the posts

Brian, our sound lad of an AI voice, puts up with reading the site aloud (he gets [a bullet of his own](/posts/this-site-1-1/#meet-the-cast) in the release post). None of the narration runs in the build or in the browser. The recordings are made on my machine with Azure AI Speech, stored in Blob Storage under a name carrying their hash, cached for a year, and played by a native `<audio controls>`. Skipping about works because the browser asks for byte ranges and the storage answers them[^http-range-requests]. No player script, no third hash.

To give Brian real personality, every second of audio is lovingly crafted by a pipeline that treats ye to a moderately enjoyable listening experience:

<Pipeline label="How a post becomes a recording" caption="Everything before Synthesise happens in a text editor. Synthesis is the only step that costs money, which is why it only redoes what changed.">
  <Step title="✍️ Write" by="Tim" human>
    Final words only: every edit after this is a re-read.
  </Step>
  <Step title="✂️ Segment" by="init">
    The MDX cut into segments by Astro's own parser.
  </Step>
  <Step title="🎚️ Tune" by="Opus and Tim" human loop="until it sounds right">
    Pauses, respellings, language tags. Opus writes them, my ears rule on them.
  </Step>
  <Step title="✅ Check" by="check">
    Same words as the post, and only the tags the voice handles well.
  </Step>
  <Step title="🎙️ Synthesise" by="Azure AI Speech">
    One request per changed segment, stitched and encoded to Ogg Opus.
  </Step>
  <Step title="📤 Publish" by="publish">
    Uploaded under a hashed name, and the manifest puts a player on the page.
  </Step>
</Pipeline>

Each recording has a tuned <abbr title="Speech Synthesis Markup Language">SSML</abbr> script beside its post, one segment per paragraph, heading, list item or diagram step. The segments are cut by the same MDX parser Astro uses, so a paragraph ends where the site says it does, and a check holds the script to the post word for word. Pauses and punctuation are mine to tune; the words aren't. Only the segments that changed are synthesised again.

Tuning is where the time goes, mine and Opus's, and Latin is the best example. The colophon in [A niche word, courtesy of Opus](/posts/a-niche-word-courtesy-of-opus/) is a paragraph of fifteenth-century Latin, and Brian's first go at it was through <abbr title="International Phonetic Alphabet">IPA</abbr>: every phrase spelt out phonetically, in his Irish accent. The second asked the voice for Italian instead, with the printer's German names in German (German names in an Italian accent would be odd). Have a listen to both:

The Roman numerals are the bit I like best: the page shows `M cccc lxxi`, and each `<sub alias>` makes Brian say the Latin word for it. The page keeps its letters and Brian gets his words, so the check still sees the same text as the post.

And the traps, because Brian has two. Edit a narrated post and `npm run check` fails, taking the deploy down with it, until Brian reads it again. Otherwise the page would happily offer a recording of words it no longer says. And the storage host is written down twice, once for the player's address and once in `media-src`, since a JSON config can't read a constant. Change one without the other and every player goes quiet on a perfectly green build.

## What's deliberately missing

- No analytics.
- No comments (we've got enough of those elsewhere).
- No third-party requests. KISS!
- No interactive islands[^astro-islands], yet! That's very much a _"let's build it when it's needed"_ - a completely valid engineering decision.
